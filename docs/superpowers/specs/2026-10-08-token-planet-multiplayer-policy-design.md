## 1. 목표와 승인 근거

Token Planet의 공유 기능에 적용할 제품 정책 기준을 하나로 정리하고, 현재 코드 경로로 두 독립 사용자가 같은 비공개 그룹에 참여하는 실제 흐름의 검증 기준을 확정한다.

각 사용자는 자신의 행성을 소유하고 성장시킨다. 그룹은 서로의 행성을 보고 정확한 사용량과 성장 수치를 비교하는 공간이다. 이후 확장은 읽기 전용 행성 방문과 공동 목표를 제공하는 방향으로 진행한다.

이번 하위 프로젝트의 결과물은 공유 정책 기준과 실제 두 사용자 검증의 수용 기준·환경 조건이다. 새로운 공유 기능이나 제품 코드 변경은 포함하지 않는다.

CEO가 전달한 사용자 설계 승인 답변은 `네, spec 작성`이며, spec 검토 요청에 대한 서면 승인 답변은 `ㅇㅇ`이다. 승인된 결정은 다음과 같다.

1. 각 멤버는 독립된 개인 행성을 유지한다.
2. 이후 확장은 읽기 전용 방문과 공동 목표를 지향한다.
3. 그룹 멤버에게 현재 행성 토큰, 누적 토큰, 성장 크레딧과 순위를 정확한 값으로 공개한다.
4. 그룹은 비공개이며 최대 10명이다.
5. 원하는 초대 정책은 7일 만료, 한 번 사용, 소유자 철회이다.
6. 기기에 묶인 익명 인증과 계정 복구 개선은 이후 단계로 미룬다.

`ㅇㅇ` 답변은 이 spec의 서면 승인이다. 구현 계획 승인 또는 검증 실행 완료는 의미하지 않는다.

후속 단계는 각각 독립적인 설계·계획·검증 범위를 가진다. 앞 단계의 위험한 미충족 사항은 의존 기능을 확장하기 전에 처리한다.

## 5. 제품 정책

### 5.1 개인 행성과 그룹

- 각 멤버는 자신의 개인 행성을 소유한다.
- 그룹 참여는 다른 멤버의 행성을 편집하거나 대신 성장시킬 권한을 부여하지 않는다.
- 그룹은 초대 기반 비공개 공간이며 공개 검색·디렉터리를 제공하지 않는다.
- 한 계정은 현재 한 그룹에 참여한다.
- 그룹 정원은 소유자를 포함하여 최대 10명이다.
- 이후 공동 목표를 추가해도 개인 행성 소유권과 성장 상태를 하나의 공동 행성으로 합치지 않는다.

두 사용자 검증은 두 명의 실제 참여 흐름을 입증한다. 10명 정원과 11번째 가입 차단의 실제 동작은 두 사용자 검증만으로 입증하지 않는다.

### 5.2 인증과 복구

현재 공유 시작 시 기기에 묶인 익명 Supabase 사용자를 생성하고 세션을 OS 보안 저장소에 보관한다. 같은 닉네임을 사용할 수 있으며 서버 계정 ID가 멤버를 구분한다.

서로 다른 두 사용자는 서로 다른 Auth 사용자와 로컬 데이터·보안 저장소를 사용해야 한다. 다른 기기를 사용하더라도 같은 프로젝트에 연결해야 같은 그룹에 참여할 수 있다.

세션을 잃으면 동일 멤버의 접근과 소유권을 복구할 수 없다. 이번 검증에서 보안 저장소를 삭제하여 복구 기능을 시험하지 않는다. 복구 구현은 이후 범위다.

### 5.3 초대

원하는 정책은 다음과 같다.

- 소유자가 발급·철회한다.
- 발급 후 7일에 만료한다.
- 한 번의 성공적인 참여에 사용한다.

현재 동작은 다음과 같다.

- 모든 사용자가 고유한 10자리 개인 코드를 갖는다.
- 현재 소유자의 코드만 해당 그룹의 참여를 허용한다.
- 소유자는 개인 코드를 재발급하여 이전 값을 무효화할 수 있다.
- 현재 개인 코드는 성공적인 참여만으로 소진되지 않는다.
- 현재 개인 코드 경로에는 7일 만료와 개별 초대 철회 관리가 없다.

이번 검증은 현재 개인 코드 참여·재발급 경로를 사용한다. 재발급은 이전 개인 코드를 무효화하는 현재 기능이며 원하는 개별 초대 철회 기능과 동일하게 취급하지 않는다.

### 5.4 동기화와 탈퇴·삭제

현재 정상 스캔·업로드 주기는 약 60초이며 실패 시 대기열을 유지하고 재시도한다. 공유 일시정지는 업로드를 중지하고 로컬 수집은 유지한다.

공유 집계 삭제는 해당 멤버의 서버 집계를 삭제하고 현재 그룹 시간대의 당일까지 기록을 이후 업로드에서 제외하며 공유를 일시정지한다. 탈퇴는 멤버십과 공유 집계를 제거하고 이 설치의 공유 대기열을 정리한다. 재참여로 제외된 과거 집계가 다시 복원되어서는 안 된다.

공유 집계 삭제를 로컬 원본 로그 삭제, Auth 계정 삭제 또는 모든 개인 행성·상점 데이터 삭제로 설명하지 않는다. 남는 데이터와 바뀐 그룹 표시를 각각 관찰하여 기록한다.

### 서버가 처리하는 데이터

인증·멤버십에 필요한 식별 정보와 기기·일자·에이전트별 집계 및 동기화 메타데이터, 공유 행성의 파생 정보를 처리한다. 개인 행성·지갑의 비공개 서버 상태와 그룹 공개 응답은 별도 경계다.

서버가 집계를 처리하는 것과 모든 멤버에게 집계 원본 행을 제공하는 것은 다르다. 그룹 밖 사용자는 해당 그룹의 행성 조회에 접근할 수 없어야 한다.

### 기기에 남는 원본 정보

- 원본 로그.
- 대화·프롬프트·도구 출력.
- 원본 파일 경로.
- 원본 에이전트의 세션·응답 식별자와 로컬 이벤트 키.

위 정보를 집계 또는 그룹 행성 payload에 포함하지 않는다. 여기서 원본 세션 식별자는 Codex·Claude Code 기록의 식별자를 뜻하며 인증 서비스 자체의 정상적인 세션 처리와 혼동하지 않는다.

Auth access·refresh token은 Rust의 OS 보안 저장소 경계를 유지한다. 그룹 공개 응답에는 지갑 잔액·적립 이력과 Auth 토큰을 포함하지 않는다.

## 7. 검증 환경과 실행 조건

### 환경 선택

local 또는 staging 중 하나의 동일한 Supabase 프로젝트를 두 사용자 모두 사용한다. production과 기존 실제 사용자 데이터는 이번 검증 대상에서 제외한다.

staging은 서로 다른 두 기기가 현재 hosted 경로로 같은 프로젝트에 연결하는 방식을 권고한다. local을 선택하려면 두 앱이 같은 local 프로젝트의 Auth·REST endpoint에 현재 지원 경로로 도달할 수 있어야 한다.

각 기기에서 별도의 local Supabase 스택을 띄우는 것은 같은 프로젝트 검증이 아니다. `dev:local`은 HTTP loopback을 요구하므로 다른 기기에서 그 launcher를 그대로 사용하여 첫 기기의 local 스택에 연결할 수 있다고 가정하지 않는다. 현재 지원 경로로 조건을 만족하지 못하면 local 검증을 환경 차단으로 기록하고 staging을 선택한다. launcher 수정은 이번 범위가 아니다.

### 실행 전 조건

- 두 독립 앱 환경 A·B와 서로 다른 익명 Auth 사용자.
- 실행 대상 앱의 정확한 경로 또는 기존 launch command.
- 동일한 검증 프로젝트, 적용된 migration 상태, Anonymous Sign-Ins 활성화.
- A·B 각각의 로컬 데이터·세션 보존 범위 확인.
- 그룹·사용량 삭제와 탈퇴가 허용된 전용 테스트 사용자·그룹.
- 집계 값의 기대 결과를 설명할 수 있는 사용 기록.
- 실행 버전·commit·플랫폼·프로젝트 구분·시간대 기록.
- payload 관찰과 테스트 앱 연결 차단의 허용 방식.

익명 계정 분리를 위해 기존 사용자의 keychain이나 SQLite를 삭제하지 않는다. 필요한 독립 환경이 없으면 해당 검증은 시작하지 않고 조건 부족을 기록한다.

원본 로그, Auth access·refresh token, 비밀 키와 개인 코드의 실제 값은 결과 문서에 저장하지 않는다. 검증에 필요한 집계 수치는 테스트 데이터 범위에서 기록할 수 있으며 사용자·그룹 식별에는 별칭을 사용한다.

CEO의 실행 brief에는 workspace, 기존 launch command 또는 앱 경로·URL, 필요한 계정·테스트 데이터와 허용 상호작용을 명시한다. 허용 상호작용에는 생성·참여·재발급·정지·재개·탈퇴·삭제·소유권 이전·RPC 관찰과 연결 차단 중 실제 수행할 항목을 포함한다.

QA는 제공된 기존 검증 환경에서 수행하며 소스·문서·테스트·설정 편집, 의존성 설치 또는 환경 구성 변경으로 부족한 조건을 보완하지 않는다. 환경이나 UI 도구가 없으면 정확한 제약과 영향을 받는 기준을 CEO에게 보고하고 해당 기준을 미검증으로 남긴다. 앱 시작·화면 로드만으로 전체 UI 동작을 입증하지 않는다. 정리 대상은 QA가 생성한 프로세스와 세션이며 기존 공유 서비스·세션을 보존한다.

### 관찰 시간

정상 연결에서 관련 업로드·조회 갱신을 5분 동안 관찰한다. 이는 현재 약 60초 동기화 주기를 고려한 검증 관찰 시간이며 제품의 갱신 SLA가 아니다.

5분 안에 기대 상태가 보이지 않으면 연결·대기열·명령 결과를 구분해 기록한다. 서버가 반영하지 않았는지, UI가 갱신하지 않았는지, 환경 접근이 차단되었는지 구분하며 단순 지연을 추측으로 통과 처리하지 않는다.

| V11 | B 탈퇴 후 B의 인증으로 이전 그룹 RPC 조회 | 서버가 멤버십 없는 B의 해당 그룹 조회를 거부한다. 화면에서 그룹을 숨기는 것만으로 입증하지 않는다 |
| V12 | 두 멤버가 있을 때 A의 소유자 탈퇴 조건과 소유권 이전 경로 확인 | 소유자 탈퇴에는 먼저 이전이 필요하고 이전 후 역할이 양쪽에 일관되게 표시된다. 이전 소유자의 코드는 해당 그룹 참여권을 제공하지 않는다 |
| V13 | 관찰 결과와 원하는 초대 정책 비교 | 현재 재사용 가능한 개인 코드와 7일 만료·한 번 사용·소유자 철회 정책의 차이를 명시한다. 원하는 정책 충족으로 판정하지 않는다 |

V04는 현재 UI의 열람 경로와 편집 동작 부재를 확인한다. UI 관찰만으로 서버의 모든 변경 API에 대한 타인 행성 수정 차단을 입증하지 않는다.

V08에서는 A의 소유자 코드로 B가 첫 참여하고, B가 탈퇴한 뒤 같은 코드로 재참여할 수 있는지 확인한다. B가 다시 탈퇴한 뒤 A가 코드를 재발급하고, B가 이전 코드와 새 코드로 각각 참여를 시도한다. 현재 코드 재사용 관찰은 한 번 사용 정책이 구현되었다는 주장과 양립하지 않는다. 실제 재참여 성공 여부와 cutoff 결과를 각각 기록한다.

V10의 당일 cutoff를 입증하려면 현재 그룹 시간대와 삭제 전후의 대상 날짜가 명확해야 한다. 다음 날 새 사용량의 재개 반영을 실행하지 못한 경우 그 부분은 미검증으로 남긴다. 시스템 시계 변경이나 새로운 테스트 전용 코드로 관찰 시간을 단축하지 않는다.

V12에서 실제 UI 경로가 동작하지 않으면 기존 공개 RPC 경로의 결과와 UI 미검증을 나누어 기록한다. 새로운 관리 UI 또는 명령 구현으로 검증을 대체하지 않는다.

소유권 이전 후 이전 소유자 A의 코드가 참여권을 잃었는지 확인할 때는 소유권을 B에게 이전한 뒤 A가 탈퇴한 상태에서 A의 이전 코드로 참여를 시도한다. 같은 상태에서 현재 소유자 B의 코드로 참여할 수 있는지도 확인한다. 이미 참여 중이라는 이유의 거부만으로 이전 소유자 코드의 무효화를 입증하지 않는다.

두 사용자만으로 확인할 수 없는 실제 10명 정원 경계, 세 번째 그룹의 격리, 다중 기기 동일 계정은 이번 실제 흐름의 증명 범위에서 제외한다. 기존 DB 테스트·소스 근거는 별도 보조 근거로 기록할 수 있다.

## 9. 검증 결과와 완료 판정

각 V01–V13과 P01–P05를 누락 없이 식별자로 보고한다. 각 기준에는 다음을 기록한다.

- 검증 방법과 범위. 문서·소스 확인인지 실제 실행 관찰인지 구분한다.
- 사용 환경·workspace·앱 경로 또는 command·URL·버전.
- 테스트 사용자·그룹 상태·관련 시간대와 UI viewport. UI가 아닌 경우 viewport는 해당 없음으로 기록한다.
- 수행 단계와 기대 결과.
- 실제 관찰 결과와 접근 가능한 증거 위치.
- 실행 상태: 통과(passed), 실패(failed), 미실행(not run), 환경 차단(environment blocked).
- 기준 판정: 입증(proven), 미충족(unmet), 미검증(unverified).
- 미검증 이유, 남은 범위와 이후 조치.

부분 확인은 확인된 범위만 입증으로 기록하고 나머지는 미검증으로 남긴다. 실행 통과만으로 기준 입증을 대신하지 않는다. 문서·소스 확인은 실제 UI·설치·동기화 동작을 입증하지 않는다.

payload 관찰을 수행하지 못하면 V05는 미검증이다. UI 화면만으로 업로드 개인정보 경계를 입증하지 않는다. 오프라인 재시도 후 최종 숫자만 확인한 경우 중복 방지의 기대값과 비교 근거가 없으면 V06의 중복 방지 부분은 미검증이다.

현재 흐름의 검증 완료와 원하는 정책 충족은 별도로 보고한다. V13은 차이를 정확하게 기록하면 이번 문서의 수용 기준을 충족하지만 원하는 초대 기능 자체는 여전히 미충족이다.

정책 문서 수용 기준:

- P01: 승인된 독립 행성·정확한 수치 공개·비공개 10명 그룹 정책을 일관되게 명시한다.
- P02: 현재 익명 인증과 개인 코드, 원하는 초대 정책을 구분한다.
- P03: 이전 이메일·OTP·개인 수치 비공개 기록을 현재 동작의 증거로 사용하지 않는다.
- P04: 데이터 공개 경계와 V01–V13의 방법·기대 결과·환경 제약을 명시한다.
- P05: 이후 기능 구현을 현재 범위에 포함하거나 완료로 주장하지 않는다.

검증 기록 작성이 실제 기능 성공을 의미하지 않는다. 미충족·미검증 항목은 그대로 보존하며 CEO가 후속 조치와 수용 여부를 판단한다. 이 두 사용자 검증은 Windows·macOS 전체 출시 승인 또는 production 배포 검증을 대체하지 않는다.

| 오래된 문서의 상반된 정책 | 기준 문서와 역사 기록을 구분하고 정합성 검토 결과 기록 |

승인된 이번 제품 정책에 남은 필수 미결정은 없다. 검증 환경·기기·테스트 데이터·payload 관찰 방법의 선택은 실행 전에 확보해야 하는 조건이며 미정 제품 요구사항으로 취급하지 않는다.

읽기 전용 방문과 공동 목표의 구체적인 UX, 기여 단위·기간·보상, 초대 구현 방식, 복구 방식은 이후 하위 프로젝트에서 별도로 설계한다.
