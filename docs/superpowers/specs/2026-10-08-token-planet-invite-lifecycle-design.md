## 1. 목표와 결정 근거

그룹 소유자가 발급한 초대를 친구가 7일 안에 한 번의 성공적인 가입에 사용할 수 있도록 하고, 소유자가 사용 전에 철회할 수 있게 한다. 현재 그룹 가입에 쓰이는 소유자 개인 코드를 초대 권한으로 대체한다.

기존 사용자 결정:

1. 각 멤버는 자기 행성을 소유하고 성장시킨다. 향후 확장은 읽기 전용 방문과 공동 목표를 지향한다.
2. 그룹 멤버에게 정확한 개인 사용량·성장 수치와 순위를 공개한다.
3. 초대는 7일 만료·한 번 사용·소유자 철회 정책을 따른다.
4. 그룹은 비공개, 최대 10명이며 현재 익명 Auth와 계정당 한 그룹 제약을 유지한다.

사용자의 “진행해”는 권고안에 따라 이 설계를 구체화하라는 승인으로 반영했다. 이는 이 문서의 서면 승인, 구현 계획 승인, 코드 변경 또는 배포 승인이 아니다.

사용자는 초안을 검토한 뒤 “ㅇㅇ”로 이 설계를 서면 승인했다. 이 승인은 이 spec에 한정되며 구현 계획·코드 변경·배포를 승인하지 않는다.

**검토 가능한 권고 가정:** 첫 버전은 현재 생성 가능한 64자리 16진수 코드를 복사·붙여넣기로 전달한다. 직접 타이핑이 주된 사용 방식이어야 한다면 코드 길이·문자 집합·추측 방어·입력 UI를 함께 재설계한다.

### 포함

- 소유자 초대 발급·목록·철회.
- 발급 후 정확히 168시간의 유효기간과 한 번의 성공 가입.
- 가입과 초대 소비의 원자성, 응답 유실 재시도.
- 가입·철회·정원·소유권 이전 경합 처리.

- 과거 초대 데이터 전환, 개인 코드 가입의 서버 차단, 구버전 동작.
- 기능·권한·동시성·실제 앱 검증 기준.

### 제외

- 계정 복구, 영구 계정 연결, 여러 기기에서 같은 계정 사용.
- 새 행성 방문 화면, 공동 목표·보상, 채팅, 실시간 공동 편집.
- 일반 멤버 식별·동기화 최신성 개선.
- 초대 링크, QR, 이메일 전송, 주소록, 공개 그룹 검색.
- 초대 철회로 이미 참여한 멤버를 탈퇴시키는 기능.
- 원본 사용량 조작 방지 및 기존 V01–V13 검증의 소급 완료 처리.

소유권 이전은 이전 소유자의 미사용 초대를 되살릴 수 없게 만드는 범위만 변경한다.

## 4. 제품 계약과 초대 상태

초대 코드는 암호학적 난수 32바이트를 lowercase 16진수 64자리로 표현한다. 원문은 발급 성공 응답에서만 반환한다. DB에는 SHA-256 해시만 저장하고 목록·오류·로그·분석 이벤트에는 원문 또는 해시를 포함하지 않는다.

| 상태 | 판정 | 새 가입 |
| --- | --- | --- |
| 사용 가능 | 미사용·미철회이며 서버 시각이 만료 시각보다 이전 | 다른 가입 조건 충족 시 허용 |
| 사용됨 | 사용 시각이 존재 | 새 가입 거부 |
| 철회됨 | 철회 시각이 존재하고 미사용 | 거부 |
| 만료됨 | 미사용·미철회이고 만료 시각 도달 | 거부 |

새 처리에서는 초대가 사용과 철회 상태를 동시에 갖지 않게 한다. 과거 자료에 두 상태가 모두 있으면 새 가입은 항상 거부하고 목록에는 사용 상태를 우선 표시한다. 만료 여부는 저장 상태로 고정하지 않고 서버 시각으로 계산한다.

그룹은 계속 비공개이고 소유자 포함 최대 10명이다. 초대 발급은 자리를 예약하지 않는다. 가입 직전에 계정당 한 그룹 제약과 그룹 정원을 다시 확인한다.

## 5. 시간 계약

- 발급 트랜잭션이 그룹 잠금을 얻고 소유자 권한을 확인한 뒤 서버가 발급 시각을 한 번 측정한다.
- 만료 시각은 expires_at = created_at + 168시간으로 설정한다.
- 절대 시각을 timestamptz에 저장한다. 시간대·DST 변화는 유효기간을 바꾸지 않는다.
- 수락은 그룹·초대 잠금을 모두 얻은 뒤 실제 서버 시각으로 유효성을 재검사한다.
- 서버 판정 시각이 만료 시각과 같거나 이후이면 새 가입을 거부한다.
- 트랜잭션 시작 시각에 고정된 now()만 사용해 잠금 대기 중 만료를 판정하지 않는다.
- UI는 지역 시각으로 만료를 표시해도 되지만 서버 판정이 최종 기준이다.

만료 직전 서버 검사를 통과해 초대 소비와 멤버십 생성을 같은 transaction에서 마친 경우 그 transaction의 정상 commit으로 가입이 완료된다.

## 6. 발급·목록·철회

### 발급

현재 그룹 소유자만 발급할 수 있다. 서버는 그룹·소유자·정원을 확인한다. 한 그룹에 여러 pending 초대를 둘 수 있고, 초대 발급은 멤버 자리를 예약하지 않는다.

성공 응답은 초대 ID, 원문 코드, 발급 시각, 만료 시각을 포함한다. UI는 원문 코드를 메모리에서만 유지하고 발급 직후 복사할 수 있게 한다. 응답을 받지 못한 코드 원문은 복구 API로 다시 가져올 수 없다. 소유자는 목록에서 해당 초대를 철회하고 새 코드를 발급한다.

### 목록

현재 소유자만 조회할 수 있다. 초대 ID, 발급·만료·철회·사용 시각과 계산된 상태를 반환한다. 코드 원문, 코드 해시, 사용자의 Auth 식별자는 반환하지 않는다. 일반 멤버에게 관리 권한을 표시하지 않는다.

### 철회

현재 소유자만 자기 그룹의 미사용 초대를 철회할 수 있다. 사용되거나 다른 그룹에 속한 초대는 철회할 수 없다. 만료됐더라도 미사용·미철회 초대는 정리 목적으로 철회할 수 있다. 반복 철회는 이미 철회된 상태를 반환하고, 성공한 가입·기존 멤버십에는 영향을 주지 않는다.

권한 확인과 상태 변경은 서버에서 수행한다. 오래된 UI의 소유자 표시는 권한 근거가 아니다.

## 7. 가입 계약과 응답 유실

입력은 양끝 공백을 제거하고 16진수 대소문자를 lowercase로 정규화한다. 정규화 후 정확히 64자리 16진수가 아니거나 비어 있으면 거부한다. 상한 길이를 먼저 확인해 큰 문자열의 해시 계산을 피한다.

새 가입은 인증된 사용자이며, 초대가 유효하고, 현재 해당 사용자의 그룹이 없고, 대상 그룹에 10명 미만일 때 허용한다. 멤버십 행 생성과 초대의 used_at, used_by 갱신은 같은 transaction에 속한다. 실패·정원 초과·이미 다른 그룹 소속·예외·commit 실패에는 사용 상태가 남지 않는다.

### 같은 사용자 재시도

가입 commit 이후 응답이 유실된 경우, 같은 사용자와 같은 초대의 재시도는 새 멤버십을 만들지 않고 성공을 재확인한다. 이를 위해 신규 멤버십에는 nullable joined_via_invite_id를 기록하고, 사용 완료 초대의 ID와 현재 멤버십의 초대 ID가 일치하는 경우에만 already_accepted를 반환한다. 이 컬럼은 world_invites.id를 참조하고 초대 삭제 시 null로 설정한다. 조회와 FK 정리를 위한 joined_via_invite_id 부분 인덱스를 둔다. 소유자 생성 멤버십과 기존 멤버십의 값은 null이다.

이 초대로 가입한 사용자가 탈퇴하면 멤버십 행이 삭제되므로 과거 초대만으로 재가입할 수 없다. 다른 초대를 사용해 다시 가입한 멤버십도 과거 초대의 재시도로 인정하지 않는다. 성공 재확인은 만료 뒤에도 허용하되 새 가입·두 번째 사용으로 처리하지 않는다.

기존 역사적 초대 사용 기록에는 이 신규 멤버십 연결이 없다. 이전 기록을 새 idempotency 동작으로 소급 변환하지 않는다.

## 8. 트랜잭션과 경쟁 처리

새 가입·철회·소유권 이전은 일관된 잠금 순서를 사용한다.

1. 초대 코드의 해시로 대상 그룹 ID를 잠금 없이 찾는다.
2. 그룹 행을 잠근다.
3. 초대 행을 잠근다.
4. 초대가 여전히 해당 그룹에 있고, 현재 소유자·발급자·상태가 유효한지 다시 확인한다.
5. 초대를 수락할 때는 잠금 뒤 만료 시각을 검사한다.
6. 사용자당 한 그룹과 10명 정원을 확인한 후 멤버십 삽입과 초대 소비를 같은 transaction에 기록한다.

알 수 없는 코드에는 그룹·초대 잠금을 시도하지 않는다. 사용자별 실패 시도 행이 필요하면 이를 그룹·초대 잠금 전에 획득하며, 모든 가입 경로에서 같은 순서를 유지한다.

예상 결과:

- 같은 초대를 동시에 수락하면 새 멤버십은 하나만 생성된다.
- 서로 다른 초대로 마지막 자리를 동시에 요청해도 정원은 10명을 넘지 않는다.
- 가입 실패는 초대를 소비하지 않는다.
- 철회가 먼저 끝나면 가입은 거부되고, 가입이 먼저 성공하면 이후 철회는 사용된 초대를 바꾸지 않는다.
- 가입과 소유권 이전은 그룹 잠금 순서로 직렬화된다. 이전 후 미사용 초대 수락은 거부된다.
- 같은 사용자가 다른 그룹에 동시에 가입하면 unique 제약으로 하나만 성공하고 실패한 초대는 미소비다.
- 소유자 탈퇴로 그룹이 삭제되면 그 그룹의 초대는 가입에 쓰일 수 없다.
- deadlock·예외·반환 오류로 부분 멤버십이나 사용 상태가 남지 않는다.

현재 가입 흐름은 초대 행을 먼저 잠그고 그룹 행을 나중에 잠그는 반면, 이전 흐름은 그룹을 먼저 잠근다. 새 수락 경로와 관련 초대 변경은 모두 그룹 → 초대 순서로 정렬한다.

## 9. 소유권 이전

소유권 이전 transaction은 그룹 행 잠금 아래에서 현재 소유자와 새 소유자의 자격을 검사한다. 이후 pending 초대를 ID 오름차순으로 잠가 모두 철회하고, 멤버 역할과 그룹 소유자를 변경한다.

사용 완료 기록은 유지한다. 만료됐지만 미사용인 초대도 철회한다. 소유권이 이전 소유자에게 돌아와도 과거 초대는 다시 활성화하지 않는다. 새 소유자가 필요하면 새 코드를 발급한다.

## 10. RPC·권한·보안 경계

계약상 필요한 RPC:

| RPC | 계약 |
| --- | --- |
| create_world_invite(world_id) | 소유자 전용. ID·코드 원문·발급·만료 시각 반환 |
| list_world_invites(world_id) | 소유자 전용. 코드 없는 초대 metadata 목록 |
| revoke_world_invite(invite_id) | 소유자 전용. 미사용 초대만 철회 |
| accept_world_invite(code) | 인증된 사용자의 결과 상태와 성공한 경우 그룹 ID 반환 |

가입 결과는 accepted, already_accepted, unavailable, already_member, world_full, rate_limited로 정리한다. 잘못된 형식·존재하지 않는 코드·만료·철회·다른 사용자가 쓴 초대는 unavailable로 통합해 초대 유효성 열거를 줄인다. 실패 결과에는 그룹 ID를 넣지 않는다. 예상하지 못한 서버 오류와 인증 실패는 정상 성공으로 변환하지 않는다.

보안 요구:

- world_invites RLS와 직접 테이블 접근 차단을 유지한다.
- 클라이언트에는 PUBLIC·anon 실행 권한을 주지 않는다. 인증된 사용자용 공개 RPC는 최소 권한만 부여한다.
- 소유자 권한은 역할명이나 클라이언트 상태로 판정하지 않는다. 서버 함수가 auth.uid()와 현재 소유자를 확인한다.
- Data API에 노출된 public RPC wrapper는 SECURITY INVOKER로 두고 authenticated에만 실행 권한을 준다. PUBLIC·anon의 기본 실행 권한은 회수한다.
- SECURITY DEFINER helper는 Data API에 노출하지 않는 private schema에 둔다. 고정 search_path, schema-qualified 객체, 내부 auth.uid()·소유자 검사를 적용한다. public wrapper가 호출할 수 있도록 helper 실행은 authenticated로 제한해 허용하되 private schema는 Data API 노출 목록에 넣지 않는다.
- Tauri/Rust가 Auth 세션을 보관한다. React에 Auth token이나 service-role key를 제공하지 않는다.
- 코드 원문·해시·Auth token은 로그·오류 문자열·분석·그룹 응답에 포함하지 않는다.
- 기존 함수 반환 타입이나 grant 변경이 필요하면 dependency를 새 migration에서 확인하고 함께 전환한다.

### 실패 시도 제한

현재 개인 코드 가입은 사용자별 시도 행으로 15분 창을 유지하고, 5회 잘못된 코드 시도 뒤 15분 차단한다. 같은 보호 수준을 새 초대 가입에 유지한다. 이 제한은 익명 Auth 사용자가 새 계정을 만들어 재시도하는 것까지 막는 보장은 아니다.

시도 행 잠금은 그룹·초대 잠금 전에 획득한다. 잘못된 형식·미존재·철회·만료·다른 사용자가 사용한 코드는 실패 횟수에 반영한다. 정원 초과 또는 이미 그룹 멤버인 상태는 추측 시도가 아니므로 실패 횟수에 넣지 않는다. 실패 횟수 갱신과 차단 결과는 정상 반환으로 transaction에 기록한다. 갱신 후 예외를 던져 카운터 변경을 rollback하지 않는다.

## 11. 데스크톱 UI

### 소유자

- 초대 발급, 코드 복사, 발급·만료 시각, 상태 목록, 미사용 초대 철회를 제공한다.
- 발급 코드는 생성 직후에만 보여주며 재조회할 수 없음을 안내한다.
- 7일·1회 사용 조건을 발급 전에 설명한다.
- 정원 도달, 응답 실패, 철회 성공·실패 상태를 명확히 표시한다.
- 그룹·소유자 변경 또는 화면 닫힘 시 코드와 오래된 비동기 응답을 폐기한다.

### 일반 멤버와 가입자

- 일반 멤버에게 초대 관리 및 개인 코드 복사·재발급을 제공하지 않는다.
- 신규 참여자는 64자리 초대 코드를 입력하거나 붙여넣는다.
- 가입 중 중복 제출을 막는다.
- 사용 불가 코드는 소유자에게 새 초대를 요청하도록 안내한다.
- 정원 초과·이미 다른 그룹 소속·일시 차단을 구분해 안내한다.
- 성공 후 서버에서 현재 공유 상태를 다시 읽어 화면을 갱신한다. 가입 RPC의 요약 응답만으로 전체 상태를 확정하지 않는다.
- 네트워크 응답 유실은 같은 코드 재시도를 허용한다.

서버 응답 이후에만 가입·철회 완료를 표시한다. 클라이언트의 표시·숨김은 권한 검사를 대체하지 않는다.

## 12. migration·구버전·전환

새 forward migration으로 정책을 바꾸며 과거 migration을 편집하지 않는다.

전환은 다음을 수행한다.

- 역사적 미사용·미철회 초대를 철회한다. 이미 사용되거나 철회된 기록은 보존한다.
- 개인 코드 테이블·사용자·그룹·멤버십을 삭제하거나 기존 개인 코드를 초대로 변환하지 않는다.
- join_world_by_member_code 실행 권한과 가입 경로를 서버에서 차단한다. 남겨 두는 조회·회전 RPC도 가입 권한을 주지 않는다.
- 새 클라이언트에서 개인 코드 조회·회전·가입 경로를 제거한다. 새 초대 RPC 실패 시 개인 코드로 fallback하지 않는다.
- 기존 그룹 구성원·집계·업로드·조회는 유지한다.
- 새 앱 준비와 격리 환경 검증 후 서버 cutover와 클라이언트 제공을 조율한다. 서버 전환 직후 구버전은 신규 가입을 못 할 수 있다.
- 구버전의 기존 가입 오류 화면에 새 안내가 나타난다고 가정하지 않는다. 업데이트 안내를 배포 문서에 명시한다.

배포는 테스트 통과만으로 자동 진행하지 않는다. production migration, 앱 배포, 외부 게시와 실제 rollback은 별도 승인 및 운영 준비가 필요하다.

## 13. 오류와 복구

- 코드를 잃으면 해시에서 원문을 복구하지 않는다. 해당 초대를 철회하고 새로 발급한다.
- 발급 응답 유실은 초대가 만들어졌을 수 있음을 안내하고 목록 확인·철회·재발급으로 회복한다.
- 가입 응답 유실은 같은 사용자·같은 초대의 already_accepted 확인으로 회복한다.
- 익명 Auth 세션 분실 복구는 이번 기능에서 제공하지 않는다.
- 초대 철회는 기존 멤버 탈퇴가 아니다.
- 장애 복구가 필요하면 새 발급·수락을 차단하는 fail-closed 절차를 우선한다. 사용·철회 기록이나 기존 멤버십을 삭제하거나 pending으로 되돌리지 않는다.
- 클라이언트 rollback에도 이전 개인 코드 가입을 자동으로 다시 열지 않는다.
- 오류 조사를 이유로 production 또는 기존 사용자 local 데이터를 reset하지 않는다.

## 15. 검증 계획과 현재 한계

검증 증거를 계층별로 구분한다.

1. migration replay 및 pgTAP: 상태 전이·권한·시간 경계·원자성.
2. 독립 DB 세션: 같은 코드, 마지막 자리, 수락 대 철회·이전의 경합.
3. Rust 검사: RPC 입력·출력, 오류 처리, 원문 비노출, 수락 후 상태 재조회.
4. React 검사: 소유자 전용 UI, 코드 복사·지우기, 철회·가입 상태.
5. 실제 두 사용자 앱: 서로 다른 Auth와 local storage, 같은 격리 Supabase 프로젝트로 정상 가입·철회·사용 후 거부.

DB 테스트는 실제 앱 동작을 증명하지 않는다. 만료 경계 시뮬레이션은 실제 7일 경과 관찰과 구분한다.

현재 공유 기능 검증은 다음 상태다.

- P01–P05: 문서 범위에서만 통과.
- V01: 일부 local onboarding 관찰. 별도 Auth 사용자·공유 시작·재시작 후 멤버십은 미검증.
- V02–V13: not run / unverified. CUA에서 임시 A 앱 창을 선택할 수 없어 UI 흐름을 시작하지 못했다.
- 격리 Supabase 서비스와 A/B 실행 환경은 준비됐으나 앱 창 접근이 복구되지 않았다.

이 상태는 신규 초대 기능의 검증 증거가 아니다. 기존 V 결과를 본 기능의 I 기준에 대체 적용하지 않는다. 새 기능 검증도 승인된 접근 경로가 없으면 environment blocked로 기록하고 소스·DB 검사만으로 실제 두 사용자 UI 완료를 주장하지 않는다.

## 16. 검토 후 진행 단계

64자리 코드의 복사·붙여넣기 가정은 사용자가 검토하며 바꿀 수 있다. 변경할 경우 코드 형식, 입력 UX, 추측 방어, API와 검증 기준을 함께 수정한다.

사용자는 2026-10-08 이 spec을 “ㅇㅇ”로 서면 승인했다. CEO는 writing-plans 절차에 따라 구현 계획을 작성한다. 계획 서면 승인과 작업 공간 준비 이후에 구현 역할에 handoff한다. 이 승인으로 구현·migration·테스트 변경이나 배포가 시작되지는 않는다.
